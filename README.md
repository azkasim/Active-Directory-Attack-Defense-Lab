# Active Directory Attack & Defense Lab

A self-hosted Active Directory environment, built from bare metal virtualization up, used to practice real internal-network attack techniques against a deliberately vulnerable (but realistic) corporate domain — then remediate each finding.

This repo documents the full build as a reproducible set of instructions, along with the attack/defense work carried out on top of it.

## Overview

- **Hypervisor:** Proxmox VE 9.2
- **Domain Controller:** Windows Server 2022 Standard, promoted to a new AD forest (`lab.local`)
- **Attacker host:** Kali Linux
- **Network:** Both VMs sit on an isolated internal bridge with no physical NIC attached — no route to the internet or the host LAN, so every technique here stays fully contained
- **Domain content:** A synthetic ~40-user "Contoso" corporate structure (departments, groups, service accounts) generated by an included PowerShell script, with a handful of intentional real-world misconfigurations built in as attack targets

## Part 1 — Build the environment

### 1.1 Create the isolated network

In Proxmox: **Node > Network > Create > Linux Bridge**.
- Name: `vmbr1`
- Bridge ports: leave empty (this is what makes it isolated — no physical NIC attached)
- IPv4/CIDR: `10.10.10.1/24` (optional, lets the Proxmox host itself reach this segment)
- Apply Configuration

### 1.2 Build the Domain Controller

1. Upload a Windows Server 2022 ISO to Proxmox (ISO Images > Upload)
2. Create VM → 4 cores, 8GB RAM, 60GB disk, network bridge `vmbr1`
3. Install Windows Server 2022 Standard (Desktop Experience)
4. Set a static IP: `10.10.10.10 / 255.255.255.0`, no gateway, DNS `127.0.0.1`
5. Rename the server (e.g. `DC01`), reboot
6. **Server Manager > Add Roles and Features** → select *Active Directory Domain Services* → Install
7. Once installed, click **Promote this server to a domain controller** → *Add a new forest* → root domain `lab.local` → set a DSRM password → finish and reboot

### 1.3 Populate the domain

Run [`AD-Population.ps1`](./AD-Population.ps1) as Domain Admin on the DC:

```powershell
Set-ExecutionPolicy Bypass -Scope Process -Force
.\AD-Population.ps1
```

This creates:
- 6 department OUs (Executive, IT, Finance, HR, Sales, Marketing) under a top-level `Contoso` OU
- ~30-45 randomly generated employee accounts with realistic titles, sorted into department-appropriate security groups
- 9 security groups modeling real permission tiers (IT-Admins, Finance-Managers, VPN-Users, etc.)
- A dedicated `admin.it` Domain Admin account, separate from the built-in Administrator
- The intentionally vulnerable accounts below

### 1.4 Build the attacker box

1. Upload the Kali Linux installer ISO to Proxmox
2. Create VM → 4 cores, 4-8GB RAM, 50GB disk, network bridge `vmbr1`
3. Run the graphical installer (manual network config: `10.10.10.20 / 255.255.255.0`, no gateway)
4. Confirm connectivity: `ping 10.10.10.10`

## Part 2 — Intentional vulnerabilities

| Account | Weakness | Attack technique |
|---|---|---|
| `svc-sql` | SPN set + member of Domain Admins | Kerberoasting → full domain compromise |
| `svc-web`, `svc-backup` | SPN set | Kerberoasting |
| `legacy.svc` | Kerberos pre-authentication disabled | AS-REP Roasting |

These mirror common real-world misconfigurations: service accounts over-privileged for convenience, and legacy accounts left with weak settings because "nothing touches them anyway."

## Part 3 — Attack chain

1. **Enumeration** — `nmap` against the DC to identify AD-relevant services (Kerberos, LDAP, SMB, DNS); unauthenticated user/share enumeration with `netexec`
2. **Attack path mapping** — `BloodHound` (SharpHound collector) to graph the path from a standard domain user to Domain Admin
3. **Kerberoasting** — Impacket's `GetUserSPNs.py` to request service tickets for `svc-sql` / `svc-web` / `svc-backup`, cracked offline with `hashcat`
4. **AS-REP Roasting** — Impacket's `GetNPUsers.py` against `legacy.svc`
5. **Domain compromise** — cracked `svc-sql` credentials (Domain Admin) used via Impacket's `psexec.py` / `wmiexec.py` to get a shell on the DC
6. **Credential extraction** — `secretsdump.py` against `NTDS.dit`, dumping every password hash in the domain to confirm full compromise

## Part 4 — Remediation

Each finding above was fixed and the corresponding attack re-run to confirm it no longer works:

- Removed `svc-sql` from Domain Admins; scoped to least privilege
- Migrated Kerberoastable service accounts toward Group Managed Service Accounts (gMSA) where practical
- Enforced AES-only Kerberos encryption (disabled RC4)
- Re-enabled Kerberos pre-authentication on `legacy.svc`
- Enabled auditing on Kerberos ticket requests (Event ID 4769) to detect future Kerberoasting attempts
